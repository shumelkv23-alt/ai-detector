Система определения
AI-сгенерированных изображений

Веб-приложение, которое по загруженному изображению определяет: это реальная фотография или картинка, сгенерированная нейросетью. Вердикт выносит ансамбль из трёх предобученных моделей, пяти forensic-анализаторов и слоя мультимодальной модели (VLM), которая детектит водяные знаки и пишет человекочитаемое объяснение.

СТЕК · Python · FastAPI · PyTorch · Vite РЕЖИМ · только CPU МОДЕЛЕЙ В АНСАМБЛЕ · 3 + VLM СИГНАЛОВ FORENSICS · 5
01

Обзор проекта

Что это, зачем и какую задачу решает.

Задача. Отличить настоящее фото от AI-генерации — нетривиально: современные генераторы (Flux, Stable Diffusion 3, Midjourney v8, Google «Nano Banana») дают фотореалистичный результат, на котором ошибаются и люди, и отдельные детекторы. Одна модель ненадёжна — поэтому проект строит ансамбль: несколько независимых источников сигнала, чьи ошибки слабо коррелируют, и аккуратная логика их объединения.

Что делает приложение. Пользователь загружает картинку (файлом или по URL) на веб-странице. Бэкенд параллельно прогоняет её через три нейросети и пять forensic-проверок, объединяет результаты во взвешенный вердикт ai / real с оценкой уверенности, а затем мультимодальная модель OpenAI проверяет наличие водяного знака и пишет понятное объяснение вердикта.

Вход

JPEG / PNG / WEBP до 10 МБ, либо публичный URL изображения.

Обработка

3 нейросети + 5 forensic-сигналов + VLM, всё параллельно через asyncio.

Выход

Вердикт, AI-вероятность, уверенность, по-модельные оценки, watermark, текстовый разбор.

Ключевые ограничения проекта (приняты осознанно). Работа только на CPU — без CUDA, чтобы запускалось на любой машине. Монорепозиторий: бэкенд и фронтенд в одном корне. Без базы данных, без авторизации, без деплоя — это учебный MVP, а не продакшн-сервис.

03

Архитектура и поток данных

Как устроен монорепозиторий и что происходит при анализе картинки.

Проект — монорепозиторий из двух частей. backend/ — FastAPI-сервис со всей ML-логикой. frontend/ — статический сайт на Vite, тонкий клиент к API. Они общаются по HTTP; в dev-режиме Vite проксирует /api/* на бэкенд.

Поток запроса /api/analyze

Картинка → валидация (MIME, размер, SSRF для URL) → декод в RGB │ ├─ 3 нейросети ┐ ├─ ELA-анализатор │ ├─ EXIF-анализатор ├─ всё параллельно: asyncio.gather ├─ Шум-анализатор │ (torch на CPU отпускает GIL) ├─ FFT-анализатор │ ├─ Watermark (YOLO) │ └─ VLM-вызов 1 ┘ (watermark, сетевой, с таймаутом) │ ▼ aggregate() — взвешенное объединение → ВЕРДИКТ ai / real │ ▼ Ответ: вердикт + по-модельные оценки + сигналы + watermark

Затем фронтенд отдельным запросом /api/explain просит VLM написать текстовое объяснение уже готового вердикта — это не задерживает показ результата.

Почему параллельно

Инференс на CPU медленный. Если гонять 3 модели и 5 анализаторов последовательно — это десятки секунд подряд. asyncio.to_thread + asyncio.gather запускают их одновременно: PyTorch на CPU отпускает GIL во время forward-прохода, поэтому потоки реально работают параллельно.

Безопасность: защита от SSRF

Эндпоинт analyze-url мог бы стать дырой: злоумышленник укажет URL вида http://127.0.0.1/... и заставит сервер ходить во внутреннюю сеть. Поэтому load_from_url резолвит хост и отклоняет приватные, loopback, link-local и зарезервированные адреса, а также не-HTTP схемы.

05

Ансамбль моделей

Три нейросети-детектора, их архитектуры и роли.

Ядро системы — три предобученные модели с Hugging Face. Главный принцип выбора — архитектурное разнообразие: модели на разных трансформерных backbone'ах ошибаются по-разному, и их ошибки слабо коррелируют. Если бы взяли три похожие модели — они бы дружно ошибались на одних и тех же картинках, и ансамбль не дал бы ничего.

МодельАрхитектураВесРоль в ансамбле
Ateeqq/ai-vs-human-image-detectorSigLIP0.30Агрессивная — хорошо ловит AI (high-recall), но склонна к ложным срабатываниям.
haywoodsloan/ai-image-detector-deploySwinV20.35Консервативная — уверенно подтверждает реальные фото (high-precision Real).
umm-maybe/AI-image-detectorViT0.35Арбитр / тай-брейкер — третий независимый голос, когда первые два спорят.

Связка устроена осмысленно: одна модель «перебдительная», другая «недоверчивая», третья — нейтральный судья. На спорной картинке агрессивная кричит «AI!», консервативная — «real!», а ViT-арбитр склоняет чашу весов. Логика агрегации (раздел 08) умеет этим пользоваться.

Patch-based detection — анализ по фрагментам

Модель смотрит на картинку целиком в разрешении 224×224. Но AI-объект, вставленный в реальное фото (composite), на уменьшенном общем снимке «растворяется». Поэтому картинка дополнительно режется на сетку 3×3 патча с 50% перекрытием (9 фрагментов), и каждый прогоняется отдельно. patch_max_ai — максимальная AI-вероятность среди патчей — ловит локальную подмену. Перекрытие гарантирует, что объект на стыке фрагментов попадёт целиком хотя бы в один патч.

Почему именно эти модели

Исходный список из ТЗ был пересмотрен — вот почему.

В техзадании предлагался другой набор моделей. При проверке оказалось, что он устарел или непригоден, и каждую замену пришлось обосновать.

МодельСтатусПричина решения
Ateeqq/ai-vs-humanвзятаСовременный SigLIP-детектор, заявленная accuracy 99%. Сильный high-recall источник.
haywoodsloan/...-deployвзятаSwinV2 ~0.2B параметров, accuracy ~98%. Оригинал был удалён с HF — используется перевыложенная deploy-версия.
umm-maybe/AI-image-detectorвзята с оговоркойОбучена в 2022 на ранних AI-картинках, слаба на современных Flux/SD3/MJ — как самостоятельный детектор плоха. Но в роли третьего независимого голоса (ViT-архитектура) усиливает медиану при разногласии. Поэтому возвращена именно как арбитр.
Organika/sdxl-detectorотклоненаУзкий специалист только по SDXL. На других генераторах бесполезна — ансамблю нужен широкий охват.
boluobobo/ItsNotAI-v2отклоненаВ config.json не заполнен id2label. На деле это 33-классовый dual-head классификатор; стандартный загрузчик берёт неверную голову, и модель на ЛЮБОМ входе выдаёт ai_prob ≈ 1.0, ломая ансамбль.
Вывод

Финальная тройка SigLIP + SwinV2 + ViT — это три разных трансформерных предобучения. Разнообразие архитектур — главная причина, по которой ансамбль точнее любой отдельной модели.

Нормализация меток

У каждой модели свой формат меток: ai/hum, ai/human, REAL/FAKE. Детектор приводит всё к единому {ai_prob, real_prob}, читая id2label каждой модели и сопоставляя по ключевым словам.

07

Forensic-анализаторы

Пять сигналов, которые ищут следы генерации без нейросетей.

Нейросети дают вероятность «на глаз». Forensic-анализаторы — другой, независимый класс сигналов: они ищут физические следы генерации или монтажа в самих пикселях и метаданных. Их сила в том, что они ошибаются не там, где нейросети.

ELA — Error Level Analysis

Пересжимает JPEG и смотрит на остаточную «энергию». Вставленная область сжималась иначе, чем фон. Доп. метрика hotspot_ratio ловит локальные подмены (composite, inpainting), когда 95% кадра чистые.

EXIF — метаданные

AI-софт в поле Software → score 0.95. Данные камеры (Make/Model) → 0.05 (признак реального фото). Нет EXIF вообще → 0.3 (соцсети их вырезают).

Шум — консистентность

В реальном снимке шум сенсора равномерен по кадру. AI-текстуры дают другую дисперсию шума. Считается коэффициент вариации локальных дисперсий.

FFT — спектр

GAN и диффузия оставляют следы в частотном спектре. Анализируется разброс радиальных спектральных профилей между патчами.

Watermark — водяные знаки

Видимые знаки AI-генераторов: YOLO-World (zero-shot по текстовым промптам) + ключевые слова в метаданных + маркеры C2PA.

Каждый анализатор отдаёт число 0..1. Эти сигналы не голосуют напрямую — они корректируют вердикт ансамбля (см. раздел 08).

08

Логика агрегации

Как голоса моделей и сигналы превращаются в один вердикт.

Наивное среднее трёх моделей не работает: первый MVP давал «вердикт-монетку». Функция aggregate() прошла через серьёзную доработку (этап «1.5»).

Медиана при разногласии

Если стандартное отклонение AI-вероятностей моделей превышает 0.25 — модели сильно спорят. Тогда вместо среднего берётся медиана: она выбрасывает экстремиста. Пример: Ateeqq=0.99, две другие ~0.2 → среднее 0.47 (монетка), а медиана 0.2 (внятный вердикт).

Patch_max только когда уже подозрительно

Максимум по патчам повышает вердикт, только если общий score уже ≥ 0.4. Иначе один странный патч на чистом фото мог бы перевернуть вердикт.

Двусторонние сигналы

Forensic-сигналы тянут вердикт в обе стороны — это ключевое:

  • AI-сигналы (ELA ≥ 0.6, EXIF ≥ 0.85, FFT ≥ 0.7, watermark ≥ 0.9) толкают вердикт вверх через max().
  • REAL-сигналы тянут вниз: данные камеры в EXIF + молчащие forensics → потолок 0.45; все forensics молчат → score умножается на 0.8 (страховка от одной слишком агрессивной модели).

Temperature scaling

Перед softmax логиты делятся на 1.5 — это смягчает «переуверенность» моделей, которые любят выдавать 0.99/0.01.

Итоговые поля вердикта

verdict = ai/real по порогу 0.5 · confidence = |0.5 − ai_prob| × 2 · disagreement = флаг сильного спора моделей.

09

VLM-слой (OpenAI)

Мультимодальная модель: детект водяных знаков + объяснение вердикта.

Финальный этап проекта — подключение мультимодальной модели OpenAI (gpt-4o, vision). Здесь было важное проектное решение.

Почему VLM — НЕ голосующая модель ансамбля

Заманчиво добавить VLM четвёртым голосом. Но современные мультимодалки — плохие классификаторы «AI или нет»: на фотореализме они уверенно ошибаются, их вывод недетерминирован и не лезет в фиксированные веса. Зато VLM отлично справляется с одной частью задачи — детектом водяных знаков, потому что это по сути OCR + распознавание логотипа. Поэтому VLM доверили ровно этот кусок и плюс — текстовое объяснение.

«Вариант B» — два отдельных вызова

ВызовГдеКогдаВлияние на вердикт
1 · Watermarkвнутри /api/analyze, параллельно с ансамблемдо агрегацииДа — кормит watermark_score
2 · Объяснениеотдельный /api/explainпосле вердиктаНет — только текст

Два вызова, потому что watermark обязан отработать до вердикта, а объяснение — наоборот, должно знать готовый вердикт, чтобы связно его объяснить. Один вызов обе роли качественно не закрывает.

Как watermark от VLM влияет на вердикт

Итоговый watermark_score = max(оффлайн-сигнал, VLM-сигнал). VLM — приоритетный источник, YOLO-World остаётся оффлайн-fallback'ом. Уверенность VLM переводится в score по линейной шкале 0.40 + 0.55 × confidence: срабатывание детектора не означает автоматически «AI на 100%».

Graceful fallback

Нет ключа OPENAI_API_KEY — VLM-слой тихо отключается: watermark считается по YOLO, /api/explain отдаёт заглушку с available:false. Система остаётся полностью запускаемой. Сетевой вызов 1 обёрнут в таймаут — если OpenAI тормозит, watermark откатывается на YOLO, а не вешает запрос.

Почему именно так, а не иначе

VLM пускают в вердикт только через watermark — там, где он надёжен — и не пускают в оценку «AI vs real», где он ошибается. Это осознанный компромисс: взять от модели её сильную сторону и не подставиться под слабую.

10

Фронтенд

Одностраничный сайт на Vite — тонкий клиент к API.

Фронтенд написан на чистом JavaScript без фреймворка — для одной страницы с загрузкой файла React был бы избыточен. Сборка — Vite 6.

Дизайн: dark terminal / forensic

Намеренная стилистика — отсылка к CLI и судебно-аналитическим инструментам: глубокий чёрный фон, моноширинная типографика, два семантических цвета — зелёный «сигнал» и красный «алерт». Вся палитра, типографика и отступы вынесены в CSS-переменные (дизайн-токены), компоненты разложены по папкам.

Поток в интерфейсе

  • Dropzone — drag-drop зоны и поле URL, переключение вкладок файл/URL.
  • Карточки результата — крупный вердикт, прогресс-бары AI/REAL по каждой модели, строка водяного знака.
  • Блок VLM-разбора — после вердикта фронт асинхронно зовёт /api/explain; пока ответ идёт — спиннер, затем текст объяснения, список признаков и «оговорка», если VLM не согласен с вердиктом.
Безопасность: защита от XSS

Текст объяснения приходит от языковой модели — это менее доверенный источник, чем собственный код. Перед вставкой в DOM все строки от VLM экранируются (escapeHtml), чтобы ответ модели не мог внедрить разметку или скрипт.

Известные ограничения

Честный список того, что стоит знать.

Производительность

Полный анализ на CPU занимает ~21–27 секунд (замер на тестовой машине) — это превышает ориентир ТЗ в 10 секунд. Причина — инференс трёх трансформеров по 9 патчей на CPU. VLM-вызов к этому не добавляет: он идёт параллельно и «прячется» под время ансамбля.

Приватность

При работающем VLM-слое изображение уходит на серверы OpenAI. Для учебного проекта приемлемо, но это нужно указать в ограничениях работы.

Стоимость и точка отказа

VLM-слой — это платные вызовы внешнего API и зависимость от интернета. Без ключа система продолжает работать (watermark на YOLO, объяснение недоступно).

Точность детекции

Ни один детектор не идеален. Цель — надёжный ансамблевый вердикт на типовых кейсах, а не 100% гарантия. Сложные composite-картинки остаются трудными.

Запуск

Как поднять проект локально.

Бэкенд

# из папки backend/
python -m venv venv
venv\Scripts\activate
pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
python run.py        # поднимет API на :8000

Первый запуск скачает ~800 МБ весов моделей в кэш Hugging Face. Для VLM-слоя — прописать OPENAI_API_KEY в backend/.env (без него слой отключается gracefully).

Фронтенд

# из папки frontend/
npm install
npm run dev          # откроет сайт на :5173

Тесты

pytest backend/tests/   # агрегация, VLM-парсеры, watermark-шкала
